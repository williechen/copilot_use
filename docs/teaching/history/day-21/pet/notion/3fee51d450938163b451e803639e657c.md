### 完整最小 Green：建立可呼叫的「驗證新增資料」流程

一、在 <code>apps/desktop_pet/src/lib.rs</code> 加入：

```rs
fn normalize_new_pet_name(input: &str) -> Result<String, String> {
    let name = input.trim();
    if name.is_empty() || name.chars().count() > 32 {
        return Err("寵物名稱須為 1 到 32 字元".into());
    }
    Ok(name.to_owned())
}

#[tauri::command]
fn validate_new_pet_name(name: String) -> Result<String, String> {
    normalize_new_pet_name(&name)
}
```

在 <code>tauri::generate_handler![</code> 現有清單最後增加 <code>validate_new_pet_name,</code>。此命令只回傳經驗證名稱；沒有悄悄把 <code>PetMachine::default()</code> 當新寵物，也不寫 DB。

二、在 <code>apps/desktop_pet/frontend/src/bridge.rs</code>，沿用檔案既有 <code>#[wasm_bindgen]</code> JS extern 區塊，新增：

```rs
#[wasm_bindgen(js_namespace = window, js_name = validateNewPetName)]
fn validate_new_pet_name_js(name: &str) -> Promise;
```

並在 bridge 外層包裝（延續此檔既有 <code>js_error</code>）：

```rs
pub async fn validate_new_pet_name(name: String) -> Result<String, String> {
    let value = JsFuture::from(validate_new_pet_name_js(&name))
        .await
        .map_err(js_error)?;
    value.as_string().ok_or_else(|| "名稱回應格式錯誤".into())
}
```

三、來源已確認 JS 橋接實作檔案是 <code>apps/desktop_pet/frontend/index.html</code>，目前透過 <code>window.__TAURI__.core.invoke</code> 暴露 <code>window.getPetState</code> 等函式。在既有 <code><script></code> 中，沿用相同模式直接新增：

```javascript
window.validateNewPetName = (name) => {
  return invoke("validate_new_pet_name", { name });
};
```

<code>bridge.rs</code> 上述 extern 使用 <code>js_namespace = window</code>、回傳 <code>Promise</code>，再由 <code>JsFuture::from</code> 包裝，符合既有 bridge 真正運作方式，不需要猜測新 JS module。四、在 <code>apps/desktop_pet/frontend/src/main.rs</code> 的 <code>App</code> 非 <code>is_pet_window()</code> 控制台分支新增輸入和驗證按鈕，狀態獨立於檔案掃描：

```rs
let (new_pet_name, set_new_pet_name) = signal(String::new());
let (new_pet_feedback, set_new_pet_feedback) = signal(String::new());
// 插入 view! 的控制台 <main class="control-shell"> 內：
<section>
    <h2>"新增寵物"</h2>
    <label>"寵物名稱"
     <input prop:value=move || new_pet_name.get()
            on:input=move |ev| set_new_pet_name.set(event_target_value(&ev)) />
    </label>
    <button type="button" on:click=move |_| {
        let proposed = new_pet_name.get_untracked();
        spawn_local(async move {
            let response = bridge::validate_new_pet_name(proposed).await;
            set_new_pet_feedback.set(match response {
                Ok(name) => format!("名稱「{name}」有效；尚未儲存寵物"),
                Err(error) => error,
            });
        });
    }>"檢查名稱"</button>
    <p role="status">{move || new_pet_feedback.get()}</p>
</section>
```

上方為需要插入現有 <code>App</code> 的完整互動片段；<b>若未先確認現有 JS extern import module 與其匯出實作，不得宣稱 Green 可執行</b>，必須先接通真正 JS → Rust invoke。不能把按鈕標「建立完成」。

### Refactor 與下一個必要環節

<b>2026-10-19 r2｜已核對 Pet Table 變更，沿用現有 Schema，不重建 </b><b><code>pet_profile</code></b><b>。</b> 來源 <code>rust_ai_chat/main</code> commit <code>5654591f3002fc619c883af9b5197e2126cc6494</code>（提交訊息 <code>modify table</code>）改動 <code>apps/desktop_pet/migrations/20261018091733_create_pet.sql</code>：在原 <code>pet_profile</code> 表新增 <code>sexy VARCHAR(255)</code>（目前 SQL 實際名稱如此，不擅自更名）和 <code>image_path VARCHAR(255)</code>。這是 <b>migration 定義更新</b>，沒有證據證明現存使用者 SQLite 已執行且成功套用。

既有 <code>pet_profile</code> 具 <code>id TEXT PRIMARY KEY</code>、<code>name VARCHAR(255) NOT NULL</code>、<code>species VARCHAR(255) NOT NULL</code>、<code>owner_id TEXT NOT NULL REFERENCES pet_owner(id)</code>、<code>age</code>、<code>ai_api_key</code>、<code>is_default_closure</code>、<code>created_at</code>、<code>updated_at</code>，另有 <code>pet_extra</code>、<code>pet_activity</code>、<code>pet_study</code>、<code>pet_life_log</code> 和 <code>codemap</code>；<code>pet_owner</code> 則由後續 migration 定義。正式新增應在既有 Schema 上建立 <code>create_pet</code>：輸入 name、species、可選 <code>sexy</code>／<code>image_path</code>，取有效 owner\_id，產生不可重複 id，驗證授權及路徑，使用 SQLite 交易原子新增，再由列表／重啟讀回並讓生活視窗綁定該寵物；不得以只驗證 name 或 <code>PetMachine::default()</code> 宣稱建立成功。<code>image_path</code> 必須遵守資產路徑驗證，AI API key 不應混入 UI 回應。

<b>升級警告：</b> 已存在的 migration 檔案被直接修改，對先前執行過舊版 migration 的資料庫可能產生 SQLx checksum mismatch。應先辨識實際套用歷史，設計保留既有 migration 的前向修補（例如對舊資料庫新增欄位）及新安裝的相容方案；不得直接修改已發佈 migration 當作可重複升級，也不能清空 DB 迴避驗證。新增資料表／欄位只能在現有 Schema 缺少且需求確定時進行。

下一個 Pet Day 應優先補<b>真正的 SQLite create→readback／重啟載入</b>，並提供舊資料庫升級測試；目前 Day21 的名稱 IPC 只是尚未套用的前置教學切片。
