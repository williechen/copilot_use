## Chat 聊天前台

#### 聊天前台互動要求
聊天前台使用 Leptos，採左側房間欄、中央訊息區、底部輸入區；個人管理與系統後台使用各自頁面／路由及後端權限，不塞進聊天訊息區。
- 首頁初次進入即自動載入公開房間列表，不要求先按「讀取／重新整理」；該按鈕保留作手動刷新。以真實 Session 決定入口文字與導向：有效登入顯示「管理」，未登入或 Session 失效顯示「登入」，後端管理授權仍須生效。
- 首頁只顯示聊天室清單與必要的載入／空／錯誤狀態；點選後進入聊天頁，建立／管理房間放個人管理頁。房間查詢須發出真實請求，具備載入、失敗恢復與重試，並保留必要的上次結果。
- 房間欄：顯示可存取房間與目前選取狀態，沿用既有列表 API；窄螢幕時可收合，切換不應把草稿送往錯誤房間。
- 訊息區：房間名稱與連線狀態固定可見，訊息以氣泡與適當寬度呈現；辨識自己、其他使用者、AI／系統。作者、時間與日期分隔只使用實際資料，缺少時明示或省略，不編造頭像、線上人數或歷史紀錄。
- 輸入區：多行輸入、送出與清楚的鍵盤操作，處理中文輸入法組字；空白／送出中禁用，保留失敗草稿。傳送中、失敗／重試等狀態須由真實協定與回應支持，不將本地送出成功冒稱伺服器已持久化。
- 使用回饋：載入、空房間引導、錯誤及重新連線狀態清楚可辨；歷史載入或重連若尚無完整後端能力，明示未接通，不顯示沒有作用的按鈕。
- 視覺與可用性：柔和背景、清楚留白與一致字體；訊息區獨立捲動，輸入區不被長訊息擠出，長文字／網址可換行。不能只靠顏色區分作者；鍵盤焦點、對比、窄螢幕與系統縮放均需驗證。
驗收從真實房間列表進房，測同房收發／跨房隔離、切房與草稿、長訊息、空／錯誤狀態、斷線、中文多行輸入及窄螢幕；無訊息確認或重試冪等能力時不能宣稱傳送狀態已完整實作。各項是否已通過以[目前進度](teaching/current/STATUS.md)的來源與證據為準，歷史瀏覽器結果不自動沿用。

## Desktop Pet

控制台與生活窗統一呈現後端 `pet_activity` 的逐寵物活動判斷：任一活動 `is_activity=true` 即出籠，全部為 false／無活動才回籠；不限散步。回籠要停止該寵物全部活動，不新增資料欄位，預設設定與目前狀態分開。不存在或不屬於本機主人的寵物回錯誤，不假冒回籠。此為已確認需求，現有產品仍須改接後才能驗收。

一個後台控制窗管理多隻寵物，各出籠寵物有獨立原生生活窗，不採放大同一張混合頁面的方式。前台寵物保留 200×200 等比動畫、拖曳、漫遊與右鍵入口；後台控制視窗承載六區功能並可縮放／捲動。關閉控制視窗後寵物繼續運作，反覆開啟只聚焦既有視窗，透過後端 snapshot／事件同步。原單視窗放大修正檔不採用，未獲授權套用至原始碼；雙窗骨架已在目前 source 存在，完整原生 GUI／IPC 尚未驗收，具體套用與驗收狀態以 STATUS 為準。

#### 控制介面：雙窗骨架已存在，其餘能力分段驗收
寵物視窗與控制視窗分工：寵物視窗保留 200×200 等比動畫、拖曳與右鍵入口；控制視窗使用 Leptos，可調整大小並可捲動，不把掃描結果、設定表單與所有按鈕堆進寵物小視窗。重複開啟只顯示／聚焦既有控制視窗，關閉控制視窗不停止寵物，不建立新寵物。
控制視窗分為六個功能區：
- 互動：狀態、互動／結束／睡覺／醒來、已有聊天入口；漫遊逐隻保存；右鍵「坐下」關閉漫遊；動作速度依種類習性，不提供固定速度設定。
- 設定：五欄與選用外觀；必須能讀回、保存及重啟保留，缺後端時明示未接通。
- 記憶：列表、查詢與管理接既有資料服務；尚無對應 API 時只顯示能力狀態，不放無作用的操作按鈕。
- 檔案：授權狀態 → 掃描／SHA256 → 結果 → 確認／取消 → 操作結果／收據 → 還原。只呈現可用 IPC；預覽確認與真實操作分開，未有操作 IPC 時明示未接通。
- 管理：多寵物、備份／還原及封存；依實作能力逐步接通。
- 更新：版本與啟動／手動檢查，依安裝與簽章更新能力接線。
控制窗依寵物識別同步各生活窗的獨立後端狀態；分頁切換不新增寵物、不自行掃描或觸發檔案動作。掃描、確認、收據與錯誤保留在對應功能區，長結果可換行／捲動且操作按鈕可到達。
驗收包含：控制視窗縮至可用小尺寸及放大、系統縮放、鍵盤焦點與捲動、長清單／錯誤文案、六區切換、反覆開啟不重複建立、關閉後寵物仍運作；專用目錄實測 UI → bridge → Tauri → OS／資料層 → 回應 → 畫面，無後端的功能不得假報成功。雙窗骨架已實作並啟動；上述完整 GUI／IPC／檔案操作尚未驗收，後續 Day 分段補齊。自動漫遊應只移動 pet 生活窗；Control 可手動拖曳，開啟／聚焦控制台沿既有 IPC。是否已通過驗收以統一進度與匹配來源的 GUI 證據為準。

## Product Analytics

#### 純後台登入與授權：需求與驗收條件
Analytics 定位為純管理後台，Leptos 提供後台畫面；除登入及必要的身分驗證流程外，所有業務頁面、查詢、管理與即時資料均須登入且具相應權限，不提供匿名 Dashboard。管理者 Session 與 Chat／Pet 服務憑證分開：服務上報／換證驗證機器身分，不以人員登入或來源 token 取代後台登入。
- 人員帳密：首次初始化 `admin/admin`，以帳號與密碼登入；登入後能修改密碼並持久保存加鹽雜湊，重啟不回復預設密碼。不得以 token 或登入碼取代帳密；實作現況以目前進度為準。
- 入口：未登入只可進入登入及必要驗證流程，不渲染或傳送業務資料；登入成功後只進入授權頁面。不提供公開業務首頁或匿名統計。
- 服務端強制：Leptos 畫面／SSR／server functions（若採用）、HTTP 查詢／管理 API 及 SSE 均檢查 Session 與操作權限；隱藏按鈕或前台 route guard 不能代替後端授權。未登入的 API 回 401，已登入但權限不足回 403；瀏覽器頁面導向登入，不先輸出敏感 SSR 資料。
- Session 生命週期：登入建立與更新有效工作階段；逾期、登出或管理者撤銷後不能繼續查詢／管理。SSE 在建立、重連及存續期間依授權政策處理失效，不能讓已登出的連線持續收到資料；具體撤銷生效期限在實作時明定與驗證。
- 管理操作：來源配對核准、憑證輪替／撤銷、封存／還原／備份等均須管理者權限與操作稽核；若使用 Cookie Session，狀態變更須有 CSRF 防護。不將來源服務的 ingestion／續期秘密交給後台瀏覽器當登入憑證。
- 機器通道：Chat／Pet 的 HTTP／gRPC 上報、配對兌換與自動換證使用各自服務身分及權限；不能開放匿名，也不要求每次自動上報由人員互動登入。一次性配對須有已登入管理者的核准交易。
- 驗收：直接輸入後台 URL、未登入呼叫 API／建立 SSE、跨權限操作、Session 到期／登出／撤銷、重連及狀態變更防護；確認沒有先洩漏頁面資料或以來源 token 越權登入。機器上報／換證與人員登入分別驗證。具體驗收與來源限制以目前進度為準。
此要求納入既有 Dashboard 與來源認證項，不新增重複 Day 或推進 next_day。

#### Leptos Dashboard：畫面與互動驗收條件
Analytics 畫面沿用 Leptos 與 Rust 元件，不以獨立手寫 HTML／JavaScript 維護另一套互動介面。先核對現有 UI crate／SSR／hydration 的責任與建置入口再接線，不為三專案檔名一致新建空骨架。
基本元件為來源選擇、事件類型篩選、查詢／重新整理、載入狀態、空資料、錯誤／重試與結果表格；由 Leptos 狀態與非同步請求呼叫現有 HTTP JSON Query API，保留來源授權與 PostgreSQL Adapter。篩選切換時清除過時結果，取消或辨識舊請求，避免晚回應覆蓋新結果。SSE 於基本查詢接通後逐步補齊。
UI 不持有 SQLx／PgPool，不另建平行 total API 或資料來源；正式管理者 Session／唯讀查詢權限與服務憑證分開，不把後端來源密鑰嵌入 WASM／HTML。來源 token 的既有學習契約保留為過渡事實，不當成正式 Dashboard 授權模型。
驗證須分別包含 native SSR（若採用）、WASM hydration／CSR、元件狀態、HTTP／來源隔離、真實 PostgreSQL 結果與瀏覽器流程；既有 API 或 CI 成功不能代替 Leptos 畫面驗收。是否完成以目前進度及適用來源的實測為準。

## Chat 聊天室清單參考要求

參考網址：http://www.utmall.com.tw/?p=chat_sort_show 。使用者提供的手機截圖顯示傳統聊天室目錄：上方功能導覽、暱稱等設定、聊天室分類橫列、密集排列的房間名稱列表，以及每列右側分類。舊站紅色 `Hit` 是畫面示例，不得當成目前 Rust AI Chat 的在線人數或活躍度；不複製其限制級警示或個人屬性欄位為產品需求。

### 已確認的互動方向

- **分類導覽＋高密度列表**：保留「分類 → 多個房間列 → 點擊進房」的主要操作模式；使用清楚可讀、可觸控的現代響應式列表，不直接複製舊站縮小桌面版。
- **房間列**：顯示真實房間名稱、可用時顯示真實分類，整列可點擊進入現有 `/room/{id}`；鍵盤焦點、目前選取狀態與行動版點擊區需清楚。沒有來源的描述、熱門數、在線數不顯示假值。
- **操作列**：首頁僅聊天室清單，建立／管理房間移至個人管理頁；搜尋、分類切換及熱門排序屬相關附加功能，必須先核對資料模型、授權過濾、API 是否支援，再決定採前端篩選或後端查詢。
- **窄螢幕**：分類可橫向捲動或換行，房間名稱過長可換行／省略並保留可存取完整名稱；避免橫向溢出；桌面可與現有左側房間欄及訊息區協作。
- **資料與狀態**：沿用既有 Leptos `chat_apps/chat_ui/src/lib.rs::RoomList`、`chat_apps/chat_ui/src/room_api.rs` 和 server 房間列表 API。載入中、空列表、請求失敗、重新整理及選房結果要有實際狀態；未完成登入／ACL 時不能宣稱私人房間隔離已驗收。
- **驗證**：真實房間清單載入／進房、分類／搜尋（若已實作）、建立後返回清單、手機及桌面視口、鍵盤、中文字與長房名、空列表／失敗／重試、跨房間隔離。UI 是否已驗收依目前進度，不由需求本文宣告。

## Chat 房間內部參考要求

使用者提供的手機截圖（瀏覽器顯示 `x5.f1.com.tw/VB/index...`）呈現傳統聊天室內部畫面：頂端工具列／選房入口、中央獨立訊息區、右側直式在線成員清單（人數標頭、暱稱及色彩區分）、底部訊息輸入與傳送及選項控制。截圖顯示的黑底、螢光黃／紫及極小字體僅供理解區域與資訊密度，**不直接複製視覺或視為可用性標準**。

### 房間內部實作要求

- 桌面／寬螢幕採房間導覽、中央聊天、右側在線成員的分區結構；主要聊天訊息與成員名單各自可捲動，底部輸入列固定在可操作位置。
- 手機／窄螢幕應以聊天訊息為主；成員名單改用可開合側欄／抽屜，避免原截圖的超窄訊息區與極小文字；顯示房名、連線狀態與返回清單。
- 在線名單、在線總數、暱稱與最後活動時間，僅在後端存在可驗證的使用者／連線狀態與授權時呈現；不得以訂閱數推算唯一在線人數，也不得製造假使用者或狀態。
- 訊息列需支援中文 IME 組字、多行輸入、送出中禁用、失敗草稿保留；文字顏色、提示音等屬可選設定，先核對現有資料與能力，不製作無效按鈕。
- 視覺採可讀對比與字級、觸控目標、鍵盤焦點；不能僅靠顏色區分成員狀態。長訊息／長暱稱／斷線重連／空列表與不同裝置尺寸需驗證。
- 本項與前節 UTMall「房間分類清單」構成「房間目錄 → 選房 → 房間內訊息＋成員 → 輸入」完整使用者流程；不把聊天室清單與在線名單混為同一資料來源。
