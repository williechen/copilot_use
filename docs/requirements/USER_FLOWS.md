### Chat：已確認的入口、註冊與管理
- 進入首頁即自動讀取並顯示房間列表，不需先按「讀取／重新整理」；載入、空列表與失敗／重試明確區分，手動刷新仍保留。首頁未登入即可查看可公開顯示的聊天室清單；點聊天室名稱連結後，未登入者先登入並保留目標房間，再由伺服器核對進入權限。有權才進房，無權顯示拒絕原因；看得到房間不代表有權進入。已登入者直接核對權限，不重複登入。
- 首頁「登入」成功後前往個人頁；已登入時文字改為「管理」，直接進個人頁。Session 失效才重新登入，成功後仍回個人頁。個人頁建立／管理自己有權管理的聊天室；系統管理另設入口並由伺服器核權。
- 一般使用者自行註冊，以唯一且不分英文大小寫的自訂帳號＋密碼登入；Email 唯一、不需驗證，用於密碼重設。註冊完成維持登出、清除原選房目標，顯示獨立完成訊息頁，不自動跳轉；只有按「回首頁」才返回清單，之後須重新選房。
- 僅首次初始化建立系統管理者 admin/admin；首次登入須修改密碼並設定唯一 Email，完成後才可使用系統管理功能；之後仍可修改密碼。密碼以加鹽雜湊持久保存，重啟不重設。

### Pet：多寵物、出入籠與活動
- 出／回籠唯一判斷來源為既有 `pet_activity`：同一主人、同一寵物，只要存在任一筆 `is_activity = true` 即出籠；所有活動都不是 true（含無活動紀錄）才是回籠。不限定活動類型，也不是只能有一筆 true。
- 建立寵物時，必須在同一筆 DB 交易建立該寵物的「散步」「坐下」兩筆 `pet_activity`，帶入相同 pet_id／owner_id；任一步失敗就整筆回滾，不留下只有寵物、缺活動的半套資料。活動存在不等於已啟用：若初始回籠，兩筆皆 false；若建立流程要求初始出籠，明確啟用選定活動，不另新增欄位。
- 「散步」is_activity=true 表示允許該隻漫遊；「坐下」is_activity=true 表示該隻仍出籠，但不允許漫遊。切換散步／坐下在同一交易互斥更新這兩筆；不得把坐下當回籠，也不另存一份漫遊旗標。散步與坐下同時為 true 時，以坐下優先：保留坐下 true，將該寵物的散步持久化為 false，停止漫遊；寵物仍出籠，不影響其他活動或其他寵物。這是正常正規化規則，不當成活動衝突。
- 出籠與切換動作使用建立時既有的活動資料，不反覆插入同名活動。回籠／原生關窗停止該寵物全部活動；仍以任一活動 true 判出籠。拖曳／睡覺的暫停移動不應清掉活動而誤判回籠；舊寵物缺少基本活動的補資料與相容性另作保資料驗證。
- 不新增出籠／回籠／啟動預設欄位，不建立第二份目前狀態；`is_default_closure` 依原欄位語意只處理預設關籠，不再當作目前出／回籠狀態。預設資格不因當次回籠而被修改。
- 控制窗有多隻寵物清單，每隻各有獨立狀態、設定與生活窗，可同時出籠；狀態同步以寵物識別分流，不將所有寵物共用一份狀態。
- 「回籠子」關閉該隻生活窗、停止活動，保留資料與設定，不刪除也不影響其他寵物；直接關生活窗等同回籠子。只有出籠寵物會活動。啟動時僅預設寵物自動出籠，可預設多隻；回籠不取消預設資格。
- 關閉控制窗不停止已出籠寵物；重開只顯示並聚焦既有控制窗。已出籠者再按出籠只聚焦自己的既有生活窗。
- 右鍵提供「開啟控制窗」「回籠子」「坐下」；開啟控制窗時自動選取自己；坐下等同關閉該隻漫遊。
- 控制窗與寵物生活窗皆可手動拖曳，自動漫遊只移動寵物，不移動控制窗。拖曳寵物時暫停漫遊，放開依原開關恢復；漫遊開關逐隻持久保存，重啟沿用。
- 走、跑、睡、跳依種類習性自然交替，不提供使用者固定速度設定。關閉漫遊時坐原地，僅保留眨眼、呼吸等細微待機動畫，不跑跳。睡覺停止自動位移，仍可手動拖曳。
- 多隻寵物可重疊並依習性互相打鬧，打鬧會吵醒睡覺的寵物；被吵醒後依種類與個性決定加入、避開或繼續睡。關閉漫遊者不參與追逐或跑跳打鬧。
- 正常活動支援跨螢幕並遵守可用工作區邊界；螢幕拔除或配置改變不立即搬回，讓寵物自行跑回。控制窗提供「找回寵物」，手動移回可見螢幕，不改漫遊設定。
### Analytics：帳號、授權、稽核與來源
- 僅首次初始化建立 admin/admin；首次登入強制改密碼並設定唯一 Email，之後可修改密碼。不開放自行註冊；由系統管理者新增帳號、初始密碼與唯一 Email，新帳號首次登入須改密碼，之後可修改或以 Email 重設。密碼加鹽雜湊持久保存，重啟不重設。
- 採系統管理者及唯讀檢視者兩角色；管理者管理帳號、來源與設定，可授權檢視者查看 Chat、Pet 或兩者。
- 2026-10-31 使用者確認：角色區分使用既有 `uac_role`（role）與 `uac_user_role`；頁面／功能管理使用 `uac_acl`（ACL）與 `uac_role_acl` 的授權關係，`uac_user_acl` 可獨立增減個別人員的功能／頁面權限：可在角色預設外新增允許，也可減去角色已授權項目；明確拒絕優先。不可在頁面 ACL 之外用硬式角色檢查使個人加權失效。角色名稱、頁面 ACL 與來源範圍分別查核，不以 hardcode admin 或只有來源判斷代替頁面管理。這是需求契約；程式採用與驗收依精確 SHA 證據判定。
- 2026-10-31 階層補充：`uac_acl` 採 `category → page → action`；category 增加「會員管理、資訊分析、認證管理」，action 對應 CRUD（新增／讀取／修改／刪除）判斷，沿用 `acl_parent_id`。角色預設與人員獨立加減權分別套用到節點；完整契約與本候選的權限組合規則見 [Analytics階層ACL](ANALYTICS_ACL.md)。
- 除登入及必要的密碼重設流程外，所有業務頁面、查詢／管理 API 與即時資料由伺服器檢查人員 Session、角色及來源範圍。帳號停用或權限縮減立即影響既有 Session 與即時連線，不等待重登。
- 帳號、權限、來源憑證及資料管理操作記錄操作者、時間、對象與結果，不保存密碼、重設連結或憑證秘密。
- Chat／Pet 各用獨立服務身分與權限，採管理者核准配對 → 短效憑證 → 自動續期／輪替 → 可撤銷。服務憑證不能代替人員後台登入。

### 2026-10-31 修改密碼補充

自身密碼保留為 ACL page。首次登入需強制修改時先顯示自身密碼頁，完成修改後，後續登入才預設顯示首頁；未完成者重登仍須先完成，不以單純登入次數繞過。 共用是同一自身密碼ACL page及實作重用，不是移除page；本人修改與管理他人帳密分別授權。先前移除page的說法已撤回，見[共用人員驗證](AUTHENTICATION.md)。

- 2026-10-31 CRUD授權補充：角色對page及其各create/read/update/delete action的授權，都必須各自保存至`uac_role_acl(role_id, acl_id)`；action的acl_id指向該page下對應的uac_acl節點。`uac_user_acl`保留個人獨立加減權，不代替角色CRUD的持久化關係。詳見[Analytics ACL](ANALYTICS_ACL.md)。

- 2026-10-31 個人CRUD授權補充：`uac_user_acl(user_id, acl_id, acl_filter)`也必須各自保存個人對page及其create/read/update/delete action的加減權；action的acl_id指向該page下的uac_acl節點。移除個人例外回到角色預設，明確減權則保存deny。角色預設仍存於uac_role_acl，不能以任一表取代另一表。詳見[Analytics ACL](ANALYTICS_ACL.md)。

- 2026-10-31 ACL分工確認：`uac_acl`只是category／page／action的定義；角色與個人權限實作分別依`uac_role_acl`與`uac_user_acl`保存的page／CRUD action授權及加減權判斷。ACL節點存在或啟用不代表已授權；沒有有效授權預設拒絕。詳見[Analytics ACL](ANALYTICS_ACL.md)。

## Chat／Analytics管理與會員授權共同規則（2026-10-31）

Chat與Analytics管理採相同邏輯：uac_acl只是定義，uac_role_acl／uac_user_acl保存角色授權與個人加減；page及CRUD action分別保存並核對。會員端mbr_perm／mbr_role_perm也是定義與角色授權的相同分工，mbr_user_perm承接個人加減。管理與會員身分、各案DB／Session仍分開；既有註冊、公開清單與逐房授權需求不變。[共用管理與會員授權契約](COMMON_AUTHORIZATION.md)。
